Project overview

A small rider-assignment API: update two riders, submit pickup/drop coordinates, claim an available candidate, read the assignment, and complete it to release the rider. HTTP handlers validate input and coordinate storage; H3 bounds lookup; Redis Lua owns atomic state changes; SQLite records successful mutations.

Location updates change coordinates and cell membership while preserving existing availability and assignment. Completion releases only the matching current assignment; repeated completion preserves its timestamp.

Candidate search is bounded to an H3 neighborhood and uses a snapshot: it does not guarantee the globally nearest rider or recheck position at claim time. Redis is a single instance (no Cluster support). There is no authentication, location expiry, routing, ETA, or Redis rehydration from SQLite after data loss. Cell sets retain busy riders; availability is filtered separately. Keys and assignment history have no TTL. SQLite write ordering assumes one API process. Redis and SQLite have no shared transaction: a 503 can follow a successful Redis mutation. Health checks Redis only.

How the project started

In a system design interview, I was asked to design a rider management system. Drawing on previous experience, I proposed Redis mappings from H3 cells to rider IDs and from each rider to their current H3 cell. The interviewer asked why I would not use a database. I explained that H3 allows us to calculate neighboring cells and use direct Redis lookups to retrieve candidate riders. The interviewer accepted the direction and requested a small AI-assisted implementation, with roughly half an hour of my involvement, to be shared through GitHub. I then discussed the take-home with ChatGPT and requested a prompt for Claude to coordinate Codex agents for implementation and testing. I specified Go, simple APIs, pickup and drop coordinates resolved to H3, and a narrow rider-assignment scope. I also required an independent implementation. An existing local system could provide broad conceptual inspiration only, with no copying. I subsequently requested documentation covering the project, the development process, the prompts, and the reasoning behind the design.

Requirements and design discussion

Why Redis for this demo?

User requirement

The requested direction uses computed neighboring H3 cells and direct Redis lookups for candidate riders. Redis also supplies the atomic claim operations in this implementation.

Why was SQLite added?

Confirmed clarification

The original spec said “Redis only, no SQL.” Mid-build the user said, “use sqlite as the db... only redis is not the correct way,” creating a conflict. Claude flagged the conflict against the interview backstory and offered three options. The user chose to keep Redis as the live/candidate-lookup/atomicity engine exactly as designed and add SQLite purely as a durable write-through system-of-record for riders/assignments. SQLite does not replace Redis, perform candidate lookup, or make atomic claims. The other options are not reproduced because their exact wording is not provided here.

What was explicitly requested?

User requirement

Go, simple APIs, pickup and drop resolved to H3, narrow rider-assignment scope, and an independent implementation with no copying from an existing local system. Routing and ETA are outside that scope; drop is recorded rather than used to plan a journey.

Reconstructed design rationale

The following Q&A are explanatory summaries of the built design, not a verbatim conversation. They distinguish observed implementation choices from recorded requirements.

Could a database alone support H3 lookups?

Implementation decision (build-time)

Yes. An application could compute H3 cells and query an indexed cell column, then use database transactions to claim riders. This demo retains the confirmed Redis architecture; SQL is not inherently incompatible with H3.

Why keep both mapping directions?

Implementation decision (build-time)

Cell sets find candidate IDs; the rider hash stores its old cell so a location update can remove old membership and add new membership atomically.

Why retain raw coordinates?

Implementation decision (build-time)

H3 narrows the candidate area; actual latitude/longitude supports haversine ranking within it and preserves the submitted pickup/drop points.

How far does search extend?

Implementation decision (build-time)

GridDisk includes the pickup cell and neighbors up to GRID_DISTANCE (default 2). The configurable bound 0–20 limits accidental expansion, but does not cap the number of riders in the cells. It is not a fixed meter radius or a global nearest search.

How is the nearest candidate selected?

Implementation decision (build-time)

SUNION gathers IDs, rider hashes supply availability and coordinates, and available candidates sort by haversine meters, then lexical rider ID. A claim can observe movement after the snapshot; it rechecks availability, not distance.

What if two requests race?

Implementation decision (build-time)

Lua checks the order mapping first and then rider availability, atomically setting the rider busy, storing the assignment, and mapping the order. A busy candidate is skipped in favor of the next ranked candidate.

What does an order retry do?

Implementation decision (build-time)

Same order ID and numerically identical pickup/drop returns the existing assignment with 200, including after completion. Changed coordinates return 409 order_payload_conflict. Float64 decoding and negative-zero normalization ignore formatting; 180 and -180 remain distinct.

How does movement change cell membership?

Implementation decision (build-time)

locationScript removes old membership, adds new membership, and updates the hash in one Lua operation. Only a newly registered rider initializes available=1; assigned riders remain busy.

How does completion safely release a rider?

Implementation decision (build-time)

completeScript marks an active assignment completed once and frees its rider only if current_assignment_id matches. Repeating completion A after claiming B cannot free B.

Which details were chosen during implementation?

Implementation decision (build-time)

The flat Go main package, h3-go/v4 v4.3.0, dispatch: key names, 201 creation / 200 replay status codes, and SQLite WAL settings are build-time decisions. See the contracts below.

What remains excluded?

Implementation decision (build-time)

No authentication, routing/ETA, cancellation, stale-rider expiry, Redis restore, Cluster support, or distributed Redis/SQLite transaction is implemented. These keep the demo focused on the requested assignment lifecycle; they are not production guarantees.

## 4. Functional scope

Implement only this flow:

1. Register a rider implicitly through a location update.
2. Convert the rider's coordinates to an H3 cell.
3. Maintain the rider's current location and H3 membership in Redis.
4. Accept an assignment request with an order ID, pickup coordinates, and drop coordinates.
5. Resolve pickup and drop to H3 cells.
6. Find an available rider near pickup.
7. Assign that rider atomically.
8. Complete the assignment and make the rider available again.

This is an API-only project. No frontend application.

## 6. Redis location model

Maintain:
- H3 cell → set of rider IDs.
- Rider ID → current H3 cell, actual coordinates, availability, and current assignment reference when applicable.
- Minimal assignment records and an order-to-assignment mapping for idempotency.

Keep all riders in their current cell sets and filter by availability during assignment.

Store actual coordinates alongside H3 cells. Use H3 for candidate discovery and actual coordinates for distance ranking.

When a rider moves:
- Remove their membership from the previous cell.
- Add membership to the new cell.
- Update their stored cell and coordinates consistently.
- Preserve their assignment and availability state.

Use a consistent Redis key prefix and document the exact final key model.

For this demo, riders do not expire automatically. Document the consequences of stale locations and explain that Redis durability depends on its configuration.

## 7. Minimal API

Use these endpoints or equally simple equivalents.

### PUT /riders/{rider_id}/location

Example request:

{
  "latitude": 28.4595,
  "longitude": 77.0266
}

Behavior:
- Creates an available rider if the rider does not exist.
- Updates coordinates and H3 membership for an existing rider.
- Does not make an assigned rider available.
- Returns the rider's current stored state.

- Assignment status.

### POST /assignments/{assignment_id}/complete

Behavior:
- Marks the assignment completed.
- Releases its associated rider.
- Repeated completion is harmless.

## 8. Candidate lookup and assignment

Use a small bounded H3 neighborhood around pickup. Make the maximum grid distance configurable, with a small default such as 2.

For simplicity:
1. Calculate the pickup cell and cells within the configured grid distance.
2. Collect rider IDs from those cells.
3. Read candidate rider state.
4. Filter for available riders.
5. Rank candidates by straight-line distance from their actual coordinates to pickup.
6. Attempt to claim candidates in that order.
7. If a candidate was claimed concurrently, try the next candidate.
8. Return a clear no-rider-available response when none can be claimed.

Use a deterministic tie-breaker such as rider ID.

Keep the search bounded. Do not expand indefinitely or claim that this finds the globally nearest rider.

Candidate discovery and ranking may use a snapshot of moving riders. Explain this limitation without adding a complex synchronization system.

The drop location is stored and converted to H3. Do not implement routing, travel-time estimation, or route optimization.

## 9. Atomicity and idempotency

Use small Redis Lua scripts or an equally clear Redis atomic mechanism for:
- Updating rider location and cell membership consistently.
- Claiming an available rider, recording the assignment, and registering the order-to-assignment mapping.
- Completing an assignment and safely releasing its rider.

Required invariants:
- One rider cannot hold two active assignments.
- One order cannot produce multiple assignments.
- Retrying a successful assignment request returns the existing assignment even if no riders are currently available.
- Conflicting payloads for an existing order return a conflict.
- Completing an old assignment cannot release a rider from a newer assignment.
- Location updates cannot overwrite assignment state.

Check order idempotency before candidate lookup and again during the atomic claim to handle concurrent requests.

Keep this scoped to one Redis instance. Redis Cluster compatibility is out of scope.

All keys have no TTL. H3 LatLngToCell resolves rider, pickup, and drop at the configured resolution. GridDisk supplies candidate cell keys; SUNION merges memberships. models.go distance uses haversine with Earth radius 6,371,000 meters and clamps rounding before asin. Sorting uses ascending distance, then rider ID.

  1. Location Lua: remove old cell membership if present, otherwise initialize availability; add new membership and update raw coordinates/cell/time.
  2. Claim Lua: check order replay/conflict before checking availability; atomically mark rider busy and write assignment plus order mapping. After all candidates, a nonexistent sentinel preserves the final concurrent-order check.
  3. Completion Lua: return missing if absent, set completion once, and release only the rider whose current assignment matches.

The order payload is canonical JSON of decoded pickup/drop float64 values. Retry and repeated completion also write through, allowing repair after an earlier SQL failure. SQLite persist upserts rider and optional assignment in one transaction, with WAL, 3-second busy timeout, and one connection. The API never reads SQLite. A process-local mutation mutex orders local Redis/read/write-through sequences; Redis Lua remains the claim authority across instances, but multi-instance SQL snapshot ordering is not solved.

Request-derived operation deadlines are 3 seconds, covering Redis and write-through. HTTP header/read/write/idle timeouts are 5/10/15/60 seconds; shutdown has 5 seconds. A SQL failure after Redis success cannot roll back the Redis claim. Forward durability is promised only for successful responses.

Known limits and future considerations

Candidate search is bounded to an H3 neighborhood and uses a snapshot: it does not guarantee the globally nearest rider or recheck position at claim time. Redis is a single instance (no Cluster support). There is no authentication, location expiry, routing, ETA, or Redis rehydration from SQLite after data loss. Cell sets retain busy riders; availability is filtered separately. Keys and assignment history have no TTL. SQLite write ordering assumes one API process. Redis and SQLite have no shared transaction: a 503 can follow a successful Redis mutation. Health checks Redis only.

Future considerations, explicitly not implemented: durable rehydration of Redis from SQLite after Redis loss, stale-rider expiry/cleanup, and coordinated SQL write ordering across API processes. These need design and verification before use.
